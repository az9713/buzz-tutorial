How Buzz works — and how you'd design it from scratch

A self-hostable Nostr relay that is also a team workspace, where AI agents are members rather than bots. This is the reasoning, not the API surface: which decisions are load-bearing, which are reversible, and what order you would think in if you were building it yourself.

1. The problem, before any architecture

A software team's memory is scattered across roughly seven systems. The conversation about why a change was made lives in Slack. The change itself lives in GitHub. Whether it passed lives in CI. Who approved it lives in the pull request. The runbook lives in Notion. The alert that started it lives in PagerDuty. The search that would connect them lives nowhere, because each system indexes only itself.

None of these systems can answer a question that spans them. "Why does this code exist?" is a join across seven databases you do not own, with no shared identity, no shared clock, and no shared notion of what an event even is. Teams paper over the gap with bots, webhooks, and a person who remembers.

Then you add AI agents, and the gap gets worse rather than better. An agent that can only see one of the seven systems is a chatbot. An agent that can see all seven needs seven API integrations, seven credential sets, and seven different permission models — and there is still no audit trail that says what it did, in order, verifiably.

Fig. 1 is the whole thesis in one picture. The Buzz README puts the ambition plainly: "one community can do what teams currently fake with chat, forges, bots, CI dashboards, release tools, search indexes, and a pile of glue code… with one substrate instead of seven tabs pretending they know about each other." Every design decision downstream is in service of collapsing that join.

2. The one bet

Buzz makes a single bet, and almost every other decision is downstream of it:

The bet Chat, git, CI, code review, workflow automation, canvases, presence, voice, and search are not seven different kinds of thing that need integrating. They are one kind of thing — a signed, typed, append-only record — differing only by a type tag. And an AI agent is not a special integration surface; it is another keypair with the same affordances as a human.

Before that sentence can mean anything, three terms need defining.

Event. The universal unit. A JSON object with exactly six fields: id (SHA-256 of a canonical serialization of the other fields), pubkey (a secp256k1 public key in hex — the author), kind (an unsigned integer type tag), tags (an array of string arrays carrying structured metadata), content (a string, often JSON), and sig (a Schnorr signature over id). This is the Nostr NIP-01 format, described in ARCHITECTURE.md §2.
Kind. A u32 integer naming the event's type. The docs are unambiguous that it is doing the heavy lifting: "the kind integer is the only dispatch switch." The relay routes, stores, and fans out by kind; clients subscribe by kind. buzz-core defines 81 kind constants and exports ALL_KINDS with 80 of them (the auth kind, 22242, is excluded because it is never stored).
Relay. The server process (buzz-relay) and the single source of truth. All reads and writes go through it. The docs are explicit about the negative space here: "There is no peer-to-peer event exchange, no gossip, no replication — just clients connecting to one relay over WebSocket."

What the bet buys you

Fig. 2 shows why one record type can carry all of that. Extension without migration. The docs state the payoff directly: "Adding a new feature means defining a new kind number; existing clients see nothing and break nothing." This is the version-tolerance property of tagged unions applied at the system level. A client subscribed to kinds 9 and 7 is structurally incapable of being broken by the introduction of kind 30621 (a multi-repository project, per docs/nips/NIP-MP.md). Compare the normal path — a new feature means a new table, a new endpoint, a new client version, and a deployment ordering constraint between them.

One search index, one audit chain, one permission check. Because git patches and chat messages are the same row shape in the same table, "search the conversation, the patch, the workflow run, and the approval in one place" (README) is not an integration project. It is a WHERE clause. The audit log covers all of them by construction rather than by seven separate implementations, and the channel-membership check that gates a message also gates the patch.

Agents get parity for free. If authorship is "whichever keypair signed it," then an agent is a member the same way a person is: it has its own key, its own channel memberships, its own audit trail. The README's framing — "Scoped by identity, not by permission flags — the same way you'd scope a teammate" — is a consequence of the event model, not an additional feature. There is no bot API to build, because there is no bot.

Third-party interoperability without an SDK. Because the wire format is standard Nostr, NOSTR.md documents connecting arbitrary NIP-29 clients straight to the relay, and the repo's own tests drive it with nak, a generic Nostr CLI. Your protocol gets clients you did not write.

What the bet costs you

CostWhere it shows up in the repo
Signature verification on every write. Schnorr verification is CPU-bound and unavoidable — you cannot trust the client. verify_event() is called under spawn_blocking in the event pipeline specifically so it does not stall the async runtime.
Relational queries get awkward. A generic event table is a poor fit for "show me this channel's top-level timeline, paged." They wrote a whole NIP for it — NIP-CW, "Channel Window": a relay-computed, cursor-paged view served as ordinary signed events through an extended NIP-01 filter.
Access control is not in the protocol. NIP-01 has no notion of a private room; the relay must impose one and get it right at every entry point. The REQ handler must check channel access before registering a subscription, and channel-scoped events are explicitly excluded from global subscriptions — both called out as deliberate security boundaries.
Client-supplied tags cannot be trusted. The h tag says which channel; a malicious client can lie. Reactions ignore the client's h tag entirely and derive the channel from the target event's e tag, failing closed on unknown targets. Kinds 44100/44101 are rejected unless signed by the relay's own key.
Privacy has to be designed per kind. A single log with full-text search will index things it should not. The search_tsv generated column contains CASE WHEN kind IN (1059, 30300, 30622) THEN NULL — gift-wrapped DMs and reminders are made unsearchable at the storage layer, because a NULL tsvector can never match.
You inherit someone else's protocol politics. Kind numbers are a shared namespace with no registry authority. Buzz carves 40000–49999 as its own range and publishes 15 draft NIPs in docs/nips/ rather than silently squatting numbers.
my read The sharpest cost is one the repo does not name as a cost: the relay must be trusted, and the bet quietly depends on that. "Every event is signed" sounds like it removes trust, but signatures only prove authorship — they say nothing about whether the relay showed you all the events, or the right ones. VISION.md confirms the model: TLS in transit, at-rest encryption delegated to the storage layer, "server-managed encryption covers every channel, every DM, every event — eDiscovery works on everything," and end-to-end encryption for DMs listed only as a future consideration. That is a deliberate, coherent choice for a corporate workspace, where discoverability is a legal requirement. But it means Buzz is self-hostable rather than trustless, and if you build something like it, you should decide which of those two words you actually meant before you write a line of code.

3. Top-down or bottom-up? A real answer

"A bit of both" is the answer people give when they have not identified which decisions are load-bearing. Here is a real one.

my read — the claim Exactly two things must be settled top-down, before any code: the event/identity model, and the tenancy boundary. Everything else — every crate, every storage engine, every client, every feature — should be built bottom-up, discovered by implementing the smallest real thing and letting the seams emerge. The reason is not taste. It is that those two decisions are the only ones that are simultaneously global (every component depends on them) and irreversible (changing them invalidates data you have already signed and stored).

Why the protocol and identity model has to be first

An event's id is a hash over its own canonical serialization, and its sig is a signature over that hash. That means the serialization rules are frozen in the data. Change how an event is canonicalized and every historical event's id stops verifying. There is no migration for that; there is only "declare the old log unverifiable." Contrast a schema change in a conventional app: add a column, backfill, ship. Cheap. The signature makes the format decision qualitatively different in kind, not just in cost.

The same logic applies to identity. The choice of secp256k1 with Schnorr signatures propagates into git commit signing (NIP-GS defines a signature format for git objects using Nostr keys through git's pluggable gpg.x509.program interface), into credential helpers (git-credential-nostr), into the auth handshake, into the pairing protocol, and into every audit entry. Buzz's own vision doc says the quiet part: "Humans and agents get the same thing: secp256k1 keypair, NIP-05 handle, Schnorr auth." Swapping the curve later is not a refactor; it is a fork.

Why tenancy is the other one

This is the decision most projects get wrong by deferring, and Buzz is a live case study — because it appears to have made the move after shipping.

Community. The tenant boundary: one workspace, one URL, one isolated world of channels, members, profiles, DMs, repos, and search. The relay resolves a TenantContext from the request host before any handler can observe tenant data — the step ARCHITECTURE.md calls "Step 0: Community Binding." An unknown host is rejected generically and never falls through to a default tenant.

The formal spec is candid about what changed: "Today a Buzz relay process is the security boundary: one DATABASE_URL, one relay keypair, one relay-global relay_members table… The model proven here demotes the relay process to stateless compute and elevates a new community entity to the tenant/security boundary, carried as a community_id on every scoped row. That move collapses a process-level boundary into a row-level one."

Collapsing a process boundary into a row boundary is exactly the retrofit that is expensive: every table, every cache key, every search filter, every audit chain, and every error string becomes a place where the boundary can leak. The tell is how much work it took to be confident it had not: a TLA+ model of the serving layer, a Tamarin model of the authorization protocol under a Dolev-Yao adversary, and a mutation test on every invariant. That is not typical multi-tenancy work. That is the price of adding a boundary late.

the docs say The spec is honest that the pattern is unremarkable: "row-level multi-tenancy with a discriminator column and row-level security (RLS) is established practice… The contribution is the formal treatment." It also states what it deliberately does not prove: liveness, performance, Postgres's own correctness, the cryptographic primitives, physical-resource isolation, and client-side leakage above the relay's interface.

The practical rule

The test for "must this be top-down?" is not "is it important?" — everything feels important. It is: if I get this wrong, does the fix require rewriting data I have already committed to, or only code? Code is cheap. Signed history is not. A schema you can migrate is not load-bearing in this sense; a hash you have already published is.

my read There is a second, softer reason the protocol goes first, and it is organizational rather than technical. VISION.md describes the build model as "Agent swarms build in parallel, integrating at the event store boundary." Parallel construction only works if the integration contract is fixed in advance. The event format is not just the data model — it is the interface that lets 26 crates and four clients be written by different workers without a coordination meeting. Deciding it top-down buys you the ability to do everything else bottom-up and concurrently. That is the actual return on the decision.

4. Why adopt Nostr instead of inventing a protocol

If you have decided the unit of everything is a signed typed record, you now face a choice that looks like a formality and is not: design that record yourself, or adopt someone else's. Buzz adopted Nostr NIP-01. Understanding why is the most transferable part of the design.

Nostr. "Notes and Other Stuff Transmitted by Relays" — a minimal open protocol where clients publish signed events to relays over WebSocket. The specifications are numbered NIPs (Nostr Implementation Possibilities). The ones that matter here: NIP-01 the event format and the EVENT/REQ/CLOSE wire messages; NIP-42 WebSocket authentication by signed challenge; NIP-98 HTTP authentication by a signed kind:27235 event; NIP-29 relay-based groups (rooms with membership); NIP-34 git repositories, patches, and status as events; NIP-11 a relay's self-description document; NIP-17 gift-wrapped private messages; NIP-25 reactions; NIP-50 search; NIP-05 human-readable name@domain handles.

What Nostr gives you free

A frozen, battle-tested serialization. Recall from §3 that the canonicalization rules are the one thing you can never change. Adopting an existing spec means that decision is already made, already reviewed by people who found the edge cases, and already implemented in libraries — Buzz pulls in the nostr crate (0.44) rather than writing its own. The single highest-consequence, lowest-differentiation decision in the whole system is one you get to skip.

Identity and auth as a solved subproblem. NIP-42 gives a challenge–response handshake; NIP-98 gives the HTTP analogue; NIP-05 gives human-readable handles. Buzz implements all three rather than inventing session tokens. The payoff is uniformity: the same keypair that authenticates a WebSocket also signs a git commit (via NIP-GS) and authenticates a CLI call.

Free clients and free tests. NOSTR.md documents third-party NIP-29 clients connecting directly, lists what works kind-by-kind, and shows the exact nak commands to send a message, react, delete, create a group, run a NIP-50 search, reply in a NIP-10 thread, and fetch NIP-17 DMs. An independent implementation of your protocol, which you did not write and cannot accidentally co-design with your server, is the best conformance test available.

A pre-solved namespace problem. Kind ranges already carry storage semantics across the ecosystem, so Buzz inherits a scheme instead of arguing about one.

What Nostr forces you to work around

Fig. 4 shows how much of that namespace discipline you inherit for free. Nostr is designed for a public, censorship-resistant, many-relay world. A corporate workspace is a private, single-relay, membership-gated world. Most of the friction traces to that mismatch.

my read Notice the shape of that table: six of the fifteen drafts are about agents. Nostr had a complete story for humans-and-relays and no story at all for "a process acting on behalf of a person, whose costs and memory and telemetry the person needs to see." That is where an existing protocol stops paying and you start writing spec. The right lesson is not "always adopt" — it is that adopting buys you the boring 80% (bytes on the wire, signatures, auth, threading, reactions, search, DMs) so your specification effort concentrates on the part that is actually new. Writing fifteen focused drafts on top of NIP-01 is a much smaller and much better-scoped job than writing one protocol from zero, and each draft can be evaluated on its own.

The counter-argument deserves a hearing. Adopting Nostr means inheriting a public-network protocol into a private-network product, and several of the workarounds above exist purely to undo assumptions you never wanted. A purpose-built protocol would have had private-by-default rooms, server-authored facts, and paging in version one, instead of as extensions. The trade you are making is: up-front design cost and a frozen format you own against permanent low-grade friction and a format you did not choose, plus an ecosystem you did not have to build. Buzz took the second. Given that the format decision is the irreversible one from §3, taking the reviewed option there and spending your novelty budget on agents is a defensible allocation.

5. The architecture, layer by layer

With the protocol settled, the runtime is almost forced. You need something that terminates WebSockets and verifies signatures, something durable to put events in, something fast to fan them out, and something cheap to put large binaries in. That is the whole system.

Why these four stores

Fig. 5 is the whole runtime on one page: five kinds of client, one relay, four stores.

Postgres holds the truth. Events, channels, memberships, workflow definitions and runs, approvals, and the audit chain all live in one database, which means a channel-membership check and an event insert can share a transaction. The events table is monthly range-partitioned, which is the standard answer to "an append-only table that only ever grows": old months become drop-a-partition rather than delete-ten-million-rows. Inserts use ON CONFLICT DO NOTHING and return (StoredEvent, was_inserted), which makes ingestion idempotent — a client that retries after a dropped connection cannot create a duplicate, because the event id is the content hash.

Redis holds only what is allowed to be lost. Presence is a key with a 180-second TTL against a 60-second heartbeat, so one missed beat cannot make a user flicker offline. Typing is a sorted set with a 5-second activity window and a 60-second key expiry to stop orphaned empty sets accumulating. Pub/sub carries cross-node fan-out. Every one of these is reconstructible from live traffic within a minute; none of it is truth. That is the discipline that lets Redis be a cache and not a second database.

the docs say The Redis subscriber uses a dedicated redis::aio::PubSub connection rather than one from the pool, and ARCHITECTURE.md says why: "pool connections cannot hold PSUBSCRIBE state." Reconnection backs off exponentially from 1 s to 30 s, and the backoff resets to 1 s only after a clean stream end — not on every attempt, which would defeat the purpose. Events published locally are tracked in an in-memory cache (AppState.local_event_ids) and skipped when they come back around the Redis loop, so a message is not delivered twice to the node that originated it.

Object storage holds bytes, not records. Media goes to S3 or MinIO through Blossom — a small protocol for content-addressed blob upload and retrieval (PUT /media/upload, GET /media/{sha256}.{ext}), capped at 50 MB. Keeping blobs out of Postgres is unglamorous and correct: it keeps the partitioned event table small enough that the index fits in memory.

Git is served, not reimplemented. The relay exposes git smart HTTP (info/refs, git-upload-pack, git-receive-pack) so ordinary git clone and git push work, plus an internal policy-check endpoint for hooks. The runtime Docker image installs git for exactly this reason. Git activity then reappears in the event log as NIP-34 events, which is how a patch ends up in the same search index as the conversation about it.

The event lifecycle — where all the correctness lives

If you read one thing in the Buzz codebase, read the EVENT handler. The ordering of its twelve stages is the entire security and performance argument of the system, and almost every stage is ordered where it is for a reason you can articulate.

Two details in Fig. 6 repay a second look.

Workflows are loop-guarded, and the guard is a design statement. Workflow execution kinds 46001–46012, relay-signed messages tagged buzz:workflow, and gift-wrap events are excluded from triggering workflows. Everything else — including ordinary chat — can trigger one. That is the minimum viable cycle-breaker for a system where automation output is indistinguishable from human input, which is precisely the situation the one-log bet creates. If you build this, you will need the same guard on day one of shipping automation.

Ephemeral events get a whole separate sub-pipeline. Presence (kind 20001) is verified, written to Redis, and fanned out locally — no membership check, no PUBLISH, and the docs note the consequence honestly: multi-node presence fan-out would need Redis pub/sub and is future work. Typing and other ephemerals do get a membership check and do ride Redis, so they work across nodes. The asymmetry is a real current limitation, not a subtlety, and it is written down.

Subscriptions: the three-tier index

Fan-out is the operation that runs on every single event, so its data structure is the one place where a naive design shows up as a production incident. Buzz keeps three DashMap-backed indexes — a DashMap is a sharded concurrent hash map, so readers on different channels do not contend on one lock.

TierIndex keyServesCost
1(channel_id, kind)Subscriptions naming both a channel and specific kinds — the overwhelmingly common caseO(1) hash lookup

The NIP-01 edge case documented here is one you would otherwise ship as a bug: an explicit empty kinds: [] array means "match nothing," while an absent kinds field means "match everything." Buzz indexes the second in tiers 2 or 3 and does not index the first at all. Absent-versus-empty is a distinction JSON makes and most deserializers quietly erase.

The access-control ordering in the REQ handler matters just as much as it does in EVENT: parse filters, extract channel, load the accessible channels for this connection's pubkey, refuse with CLOSED "restricted: not a channel member" if it does not match, and only then register the subscription. Registering first and checking after would open a window in which live events from a private channel reach a non-member — a race, not a hypothetical, because fan-out is concurrent with the check.

The crate decomposition — 26 crates and the rule that makes them work

Twenty-six crates in one Cargo workspace is a strong opinion. The opinion is not "small modules are nice." It is a specific dependency rule, and the rule is what makes the count sustainable.

Fig. 7 draws that rule. The stated principle is worth quoting exactly: "The relay is the single source of truth. buzz-relay orchestrates all subsystems by calling them directly… However, those subsystems are isolated from each other: buzz-workflow never calls buzz-pubsub, buzz-search never calls buzz-db, etc. Cross-subsystem coordination happens only through the relay."

That is a star topology enforced by the compiler. Cargo will not let buzz-search call into buzz-db if it does not list it as a dependency, so the architecture diagram cannot silently rot into a mesh — which is the normal fate of layering rules that live only in a document. It also means every cross-cutting concern has exactly one place it can be implemented, and you always know where to look.

my read — why zero-I/O core is the highest-leverage crate buzz-core banning tokio, sqlx, redis, and axum in its manifest looks like purity theatre until you notice what it buys. First, the rules are testable without infrastructure: filter matching, signature verification, and the SSRF private-IP check are pure functions, so they can be property-tested (the workspace pulls in proptest) with no Postgres running — and those are exactly the functions where a subtle bug is a security bug. Second, it forces the interesting decisions into the open: if the type that represents a stored event cannot reach a database, then whoever does reach the database has to state the contract explicitly. Third, it is the only way to keep 26 crates from becoming 26 tangles — a bottom layer that cannot depend on anything is a bottom layer that everything can depend on safely. My suggestion for a from-scratch build: write this crate first and let it be the thing you are proud of.

One more detail in that manifest is worth copying. StoredEvent carries a private verified: bool field with an is_verified() accessor. Privacy of a field is how you make "this event's signature has been checked" un-forgeable within your own codebase: no other module can construct a verified-looking event by setting a boolean. That is using the type system as an audit control, and it costs nothing.

6. The agent surface

"Agents are members, not bots" reads like positioning. It is actually a load-bearing architectural claim, and the difference shows up in five concrete places. Some vocabulary first.

MCP (Model Context Protocol). A JSON-RPC protocol by which a model-driven agent calls tools — a shell, a file editor, a search index. The agent is the client; the tool provider is the server.
ACP (Agent Client Protocol). A JSON-RPC-over-stdio protocol by which an application drives an agent. The handshake is initialize, then session/new (returning a sessionId), then session/prompt, which streams session/update notifications and returns a stopReason. Editors like Zed and JetBrains speak it, which is why an ACP-compliant agent works in an editor and in Buzz without an adapter.
Harness. buzz-acp — the process that sits between the relay and the agent subprocesses. It holds a Nostr identity, subscribes to the relay, batches incoming @mentions, and drives agents over ACP.

What "member, not bot" actually changes

Fig. 8 traces one @mention from the log to a tool call and back. Five consequences follow from that shape.

1. Authorization is identity, not a flag. A bot API is a parallel permission system: bot tokens, bot scopes, a bot's-eye view of the world that drifts from the human one. Here an agent has a keypair, appears in channel_members with role Bot, and is gated by the same membership check as everyone else. Removing an agent from a channel is the same operation as removing a person. There is no second code path to audit — which also means there is no second code path to get wrong.

2. Provenance had to be specified, not hand-waved. This is where the design earns its claim. When an agent acts for a person, whose action is it? NIP-OA defines an auth tag by which an owner key authorizes an agent key to publish "under the agent's own authorship," and it explicitly refuses the obvious shortcut: NIP-26 delegation "assigns the event to the delegator semantically, and that semantic MUST NOT be reused for agent provenance." In other words, the log must record that the agent did it, with the owner visible as the authorizer — not that the owner did it. That distinction is what makes the audit trail meaningful once agents are numerous.

3. Onboarding becomes transitive. NIP-AA builds on that: an agent whose owner is a relay member gains implicit access by presenting its NIP-OA credential during NIP-42 authentication, without being separately enrolled. Compare the alternative, where every agent is an admin ticket. The scaling target in VISION.md is 10 000 humans and 50 000 agents — a five-to-one ratio that makes manual enrolment obviously untenable.

4. Costs and memory belong to the owner, not the platform. NIP-AM records per-turn token usage and cost as kind:44200 events encrypted to the owner, "so the owner can account for token usage across agents and harnesses without the relay — or any third party — learning what the agent did or what it cost." NIP-AE stores agent memory as encrypted kind:30174 events using the symmetric agent↔owner conversation key, with the deliberate consequence that "the owner can always read everything the agent remembers." Both are the same move: agent state is the owner's data, living in the same log, under the owner's key.

5. The tool surface is designed for a machine reader. buzz-cli is "JSON in, JSON out" with structured errors on stderr — described in VISION.md as "designed for LLM tool calls." That is a real constraint, not a slogan: stdout must be parseable without heuristics, errors must be machine-classifiable, and the surface must be self-describing enough to become tool definitions. Human-first CLIs fail all three.

Backpressure, or why the queue is the interesting part

The single most important line in the harness design is that at most one prompt is in flight per channel, with subsequent mentions queued and later batched into one prompt. A busy channel that mentions an agent ten times produces one conversation, not ten concurrent agents racing to answer and posting five contradictory replies.

Look at where the bounds live and a pattern emerges. Buzz bounds everything, and it prefers refusing to queueing:

my read That table is the real answer to "what changes when agents are members." Agents do not get tired, do not notice they are being rude, and can generate load at machine rate through the exact same API as a person. A system that gives agents human affordances must therefore give every affordance a bound, because the polite-human assumption that used to hold the system up is gone. Notice how many of these prefer immediate refusal to queueing — try_acquire rather than acquire, CapacityExceeded rather than a backlog. That is the right default under machine load: a queue you cannot drain is just latency plus an eventual crash, whereas a refusal is a signal the caller can act on. Buzz's own known-limitations list admits rate limiting is not implemented — the RateLimiter trait exists with only a test stub — which makes the semaphores the only thing actually holding the line today.

Personas: separating identity from process

A persona is a saved agent identity — display name, avatar, system prompt, model and runtime choice, environment variables — held independently of any running process (NIP-AP makes it a public addressable kind:30175 event; the desktop app stores the local half). A managed agent is a process the desktop app spawns and supervises against that persona. The useful consequence, documented in key-concepts.md: persona environment variables are read live at spawn time, so rotating a credential on the persona takes effect on the next spawn of every agent using it, with no per-agent edit. A persona pack bundles personas, skills, MCP server config, hooks, and distribution metadata into a portable zip or git repo — a superset of the Open Plugin Spec.

The layering — persona (what it is) / process (a running instance) / pack (how it is distributed) — is the same separation container images made routine, applied to agent configuration. It is the difference between "my agent" being a machine you must not lose and being a document you can hand to a colleague.

Workflows: the deterministic half

Not everything that acts automatically should be a language model. buzz-workflow is the deterministic complement: channel-scoped YAML with four triggers (message_posted, reaction_added, schedule, webhook) and seven actions (send_message, send_dm, set_channel_topic, add_reaction, call_webhook, request_approval, delay).

name: "Incident Triage"
trigger:
  on: message_posted
  filter: "str_contains(trigger_text, 'P1')"
steps:
  - id: notify
    action: send_message
    text: "P1 incident detected: {{trigger.text}}"
  - id: page
    if: "str_contains(trigger_text, 'production')"
    action: request_approval
    from: "{{trigger.author}}"
    message: "Page on-call?"

The engineering details are more instructive than the DSL. Conditions are evaluated by evalexpr against a flat context in which dot notation is rewritten to underscores (trigger.text becomes trigger_text), with four registered string functions and a 100 ms timeout so a hostile expression cannot occupy a worker. Step ids are restricted to alphanumerics and underscore explicitly to prevent injection into that expression namespace. Template substitution is single-pass and non-recursive, and unknown variables are left as literal text — a deliberately boring choice that removes an entire class of expansion attack. Outbound call_webhook requests get SSRF protection (the shared is_private_ip check in buzz-core, covering loopback, private ranges, link-local, CGNAT, IPv6 ULA, and IPv4-mapped IPv6), redirects disabled, and a 1 MiB response cap. Approval tokens are CSPRNG UUIDs stored as SHA-256 hashes, and single use is enforced in SQL with AND status = 'pending' on the UPDATE rather than in application code.

Each of those is a small decision. Together they are the difference between a workflow engine and a remote code execution vector, since the whole point is that channel members can author automation.

my read — the FTS choice is the best decision in the stack Postgres full-text search will lose a relevance bake-off against a dedicated engine. It wins on something that matters more here. A separate search service means a dual write, which means a window where a message exists and is not findable, which means reconciliation, backfill jobs, and an entire failure mode. Buzz's version is a generated tsvector column: the index is part of the row, committed by the same transaction, and it is impossible for an event to be stored but unindexed. The privacy control rides along for free — CASE WHEN kind IN (1059, 30300, 30622) THEN NULL makes gift-wrapped DMs and encrypted reminders unsearchable at the storage layer rather than by remembering to filter at query time. In a separate engine that same rule would be an indexer branch, and forgetting it would leak DMs into search. Choose the boring one and revisit only when relevance is a measured complaint.

One nuance worth copying regardless of engine: buzz-search deliberately does not enforce access control. It returns candidate hits, and "the relay re-authorizes each one (channel membership, #p, owner gates) before delivering it." That separation is what keeps the search engine swappable — permissions never leak into the index — and it also means a bug in search cannot become a data leak on its own.

Multi-stage Docker with cargo-chef. Eight stages: a chef stage computes a dependency recipe, a planner stage cooks it, and only then does the source layer build — so an unchanged Cargo.lock means a cached dependency build. Writing down why you accepted a known vulnerability, next to the path that causes it, is the difference between a security process and a green checkmark. Alongside it: Biome for JS/TS lint and format, clippy with -D warnings, lefthook pre-commit hooks, Renovate for dependency updates, and a bespoke CI job that greps client code for dead auth-token identifiers to stop a removed mechanism creeping back.

my read If you copy one non-obvious thing from this stack, make it the pinning. A protocol-first system with 26 crates, four clients, and two ecosystems has an enormous surface for "works on my machine." Hermit collapses it to one command, and it is the reason a contributor's first experience is just setup && just build rather than an afternoon. The architecture gets written about; this is what determines whether anyone else can work on it.

8. Build order

Here is a concrete sequence, each stage tied to the crate that would embody it. The ordering principle is the one from §3: anything that gets frozen into stored data comes first; anything that is only code can wait.

Stage by stage

Fig. 9 shows the taper; here is each stage in words.

1 · buzz-core — the event and nothing else. Types, canonical serialization, id derivation, Schnorr verify, NIP-01 filter matching (OR across filters, AND within one, including id prefix matching), and the kind registry with its ranges reserved up front. No I/O — forbid the runtime in the manifest, as Buzz does, so the ban is mechanical rather than aspirational. Property-test the filter matcher here; it is the function whose bugs become either missed messages or leaked ones. You cannot defer this, because everything else is a consumer of it.

2 · Tenancy binding, before you have a second tenant. Even if you will only ever run one community, resolve it from the request host at the connection boundary and thread it through as an explicit context. The plumbing is nearly free at N = 1 and near-impossible to add at N = 1 000 000 rows — which is the whole lesson of the multi-tenant spec. Make unknown hosts fail closed from day one, never defaulting to a fallback tenant.

3 · buzz-db — storage, with retention designed in. The events table, partitioning, and idempotent insert. Do ON CONFLICT DO NOTHING immediately; retry-safety costs one clause now and a deduplication project later. Partition by time from the first migration — repartitioning a large live table is genuinely miserable. Buzz is at 26 migrations, which is a reasonable calibration for how much schema movement to expect.

4 · buzz-auth — identity and the single gate. NIP-42 for the socket with a bounded timestamp tolerance (±60 s), NIP-98 for HTTP, and channel membership as the only authorization concept. Resist a second one. The moment you have both "membership" and "permissions," you have two systems that can disagree, and the disagreement is the vulnerability. Make membership operations transactional so check-then-modify cannot race, and soft-delete members (a removed_at column) so re-adding is reversible and history survives.

5 · buzz-relay — the socket, the pipeline, the registry. The connection lifecycle (semaphore, challenge, auth, then three coordinated loops for receive, send, and heartbeat, with a cancellation token to shut them down together), the ordered EVENT pipeline, and the REQ path with its access check before registration. Build the three-tier subscription index now rather than a linear scan you plan to optimize — the index shape determines the fan-out ordering rules, and those are semantics, not performance.

my read — the one you must not defer that looks deferrable Stage 4's fan-out exclusion rule. "Channel-scoped events are never delivered to a global subscription, even if the filter matches" sounds like a refinement you would add once private channels exist. It is not. It is a rule about which index a delivery is allowed to consult, and retrofitting it means auditing every delivery path in a system that already has users. Write the private-channel boundary into the fan-out on the first day you write fan-out, even if every channel is public.

6 · buzz-audit — the hash chain. Each entry hashes the previous one, so tampering with any entry invalidates everything after it. The implementation notes are worth copying wholesale: hash a canonical serialization with BTreeMap-ordered keys so it is reproducible, take a pg_advisory_lock so there is exactly one writer, and release that lock on every path including panic via catch_unwind — an advisory lock leaked by a panic wedges the chain for everyone. Ten action types is a good starting vocabulary. You can add this later, but you will not have the earlier history, so add it before anyone depends on the log.

7 · Search, presence, media. All three are rebuildable from the event log, which is what makes them deferrable. Search as a generated column costs one migration; presence and typing are Redis keys with TTLs; media is an S3 bucket and an upload endpoint. Get the privacy exclusions into the search column at the moment you create it, though — retroactively un-indexing DMs means a reindex.

8 · The agent surface — CLI first, harness second. Order matters here. Build buzz-cli (JSON in, JSON out) before buzz-acp, because the CLI is the agent's write path and the harness only supplies the read path. A CLI with no harness still gives you scriptable agents and a testable surface; a harness with no CLI gives you an agent that can be woken up and cannot answer. And building the CLI first forces the API to be machine-shaped early, which is much harder to retrofit onto a human-shaped one.

9 · Everything else. Workflows, git hosting, huddles, canvases, forums, desktop, mobile. Each is genuinely additive under the one-log bet: a new kind, a new handler, a new surface. This is the payoff for the discipline of the first five stages — by stage 9, adding a feature is not an architectural event.

9. What's actually hard

Two sources in the repo tell you where the real difficulty is, and they tell you in opposite ways. ARCHITECTURE.md §9 lists six known limitations — the things that are unfinished. docs/spec/ and docs/formal/ contain machine-checked proofs — the things that were frightening enough to prove. Read together, they map the risk surface better than any prose summary.

The admitted gaps

#LimitationWhat it actually means
1No sqlx offline query cache — runtime sqlx::query(), not the checked macroSQL errors surface at runtime, not compile time. A tooling debt, cheap to pay down, and the only reason it persists is that the macro form requires a live database at build time.
2No rate limiting. The RateLimiter trait exists; the only implementation is a test stub that always allows. Four tiers (human, agent-standard, agent-elevated, agent-platform) are defined as a design target and enforced nowhere.The most consequential gap on the list. In a system explicitly designed for 50 000 agents, the only backpressure is semaphores and connection caps. A well-meaning agent in a retry loop is currently indistinguishable from an attack.
3No REST endpoint for typing stateCosmetic. Typing is delivered live; you just cannot query "who is typing now."

5Approval gates not wired end to end. The executor returns Suspended, the DB and REST endpoints exist, but the engine intercepts before creating a WaitingApproval row — so a run that hits an approval gate is marked Failed.The genuinely hard one. See below.

Limitation 5 deserves attention because it is the same problem in every workflow engine ever built, and it is worth understanding before you design your own DSL. A step that waits for a human turns your executor from a function into a state machine that must survive process restarts. You now need durable execution state, resumption from an arbitrary step, a timeout with its own scheduler, single-use token semantics, and a coherent answer for what happens when a deploy lands mid-wait. Buzz has the ingredients — execute_from_step() exists, approval tokens are CSPRNG UUIDs stored as SHA-256 hashes with single-use enforced in the SQL UPDATE — and has not yet assembled them.

my read The design lesson is about ordering, not about workflows. Suspension is the feature that turns a stateless evaluator into a durable orchestrator, and that is a different program. If you know you want approval gates, either build the executor as a persisted state machine from the first line — or ship without the step. The current middle state, where the step exists in the DSL and marks runs failed, is the worst of the three, because a user can author a workflow the engine promises to run and then does not.

Where they reached for formal methods

Now the more interesting signal. Formal verification is expensive; nobody does it for fun. What a team chooses to prove tells you which failures they judged both plausible and catastrophic — and in this repo the answer is unambiguous.

TLA+ is a specification language for concurrent and distributed systems; its model checker (TLC) explores every reachable interleaving of a bounded model and reports a counterexample trace when an invariant breaks. Tamarin is a symbolic protocol verifier that proves properties against a Dolev-Yao adversary — an attacker who controls the entire network, can read, drop, reorder, and forge any message, but cannot break cryptography. Mutation testing, in this context, means deliberately weakening a check and requiring the model to fail — the proof that your invariant is not vacuously true.

Fig. 10 collects the four modelled areas. Multi-tenancy is the top risk, and they knew it. The spec's own framing: demoting a process-level security boundary to a row-level one "collapses a process-level boundary into a row-level one. The contribution of this document is the formal characterization that the collapse loses nothing." Crucially it states isolation as non-interference encoded as a label-flow invariant — not as "every query has WHERE community_id = $1." Those are different claims. The second is a coding convention you can forget in one query; the first is a property of the whole interface, including error messages and audit contents. Note what counts as an observable there: error strings. A distinguishable error is an oracle, and it is the leak nobody writes a test for.

Git on object storage is about lost writes. Two pushers racing to advance one ref pointer is the classic compare-and-swap problem, and the failure mode — a commit that the client was told succeeded and that is not there — is silent and unrecoverable. The model asserts that installs form a fork-free chain and that each commits exactly the value it proposed, derived from the pointer it read. If you are putting git refs anywhere other than a filesystem with real locking, this is the property you need.

Push notifications are about content disclosure. A push payload leaves your infrastructure and traverses Apple's. The model requires the body to be byte-identical to a fixed constant under every relay-controlled and gateway-state input, with a mutation test that injects each prohibited input category and requires it to be caught. That is how you get a notification system that cannot leak message text even by accident.

the docs say — the honesty is the strongest part Each formal artefact states its own limits. The multi-tenant spec disclaims liveness, performance, Postgres's internal correctness, the crypto primitives, physical-resource isolation, and client-side leakage above the relay's interface — and argues that stating the boundary is part of the claim: "'Provably isolated' without naming the trust boundary does not survive scrutiny." The NIP-PL note is equally direct: the models "enumerate bounded abstract transitions, not SQL schedules or network behavior," a crash after APNs accepts but before persistence "remains intentionally at-least-once," and a constant payload "prevents content disclosure but cannot hide wake timing or frequency."

What all of this tells a from-scratch builder

Line the two lists up and a pattern falls out. The admitted gaps are all execution problems — code that is not written yet, states not persisted, an implementation missing behind a trait. The proved properties are all boundary problems — data crossing between parties who must not see each other, or a write disappearing under concurrency.

That is the real risk map of this class of system, and it inverts the intuition. The hard parts are not the features. Chat, reactions, threads, canvases, media, and even voice are legible, testable work you can grind through. The hard parts are: the boundary between tenants, the boundary between what the relay knows and what it should be able to see, the boundary between an owner and their agent, and the moments where two writers race. Those are the places where a bug is silent, catastrophic, and unreachable by ordinary tests — which is precisely why the team spent TLA+ and Tamarin budget on them and not on the chat.

The corollary for your own build: when you are deciding where to spend disproportionate care, do not ask which feature is biggest. Ask which failure would be invisible.

The argument in one page

Buzz makes one bet — that everything a team does is a signed typed record in one log, and that an agent is just another keypair — and then follows it honestly. Following it honestly is the whole discipline: it means a kind registry instead of a table per feature, membership as the only authorization concept instead of a permission matrix, a star-shaped crate graph the compiler enforces instead of a layering doc nobody reads, and a bound on every affordance because agents do not self-moderate. The two decisions that had to be made top-down — the event format with its frozen serialization, and the tenancy boundary resolved from the host before any handler runs — were made top-down; the twenty-six crates, four clients, and four backing stores underneath were discovered bottom-up and remain individually replaceable. Where the protocol they adopted did not reach, they wrote fifteen specifications rather than proprietary fields, and where they judged a failure would be silent rather than loud, they reached for a model checker. The gaps that remain are unfinished code. The parts that are built are solid at the boundaries, which is the right way round.
