The Buzz trust map

Six things Buzz is expected to keep safe. For each one: the single mechanism that actually enforces it, the single artifact that verifies that mechanism, and whether that verification is switched on in a default production deployment. Four of the six answers are weaker or differently shaped than the architecture documents lead you to expect.

What this document is, and how to read it

Buzz is a self-hostable Nostr relay that doubles as a team workspace where AI agents are members rather than bots. Like any such system, it carries a set of implicit promises: your private messages stay private, only members see a channel, one organisation's data does not leak into another's, an agent cannot do more than it is allowed, and uploaded files are not world-readable.

This document takes each of those promises and asks three questions in order. They are deliberately narrow.

  1. What actually stops it from breaking? Not what the documentation says — the specific thing in the running code. Is it mathematics (encryption nobody can undo)? A database predicate (WHERE community_id = $1)? A schema constraint the database itself refuses to violate? A compile-time fence? A hardcoded allowlist? Or — the weakest kind — a paragraph of English in a prompt file, politely asking a language model to behave?
  2. What proves that thing works? A test, a formal proof, a runtime monitor, or nothing.
  3. Is that proof switched on in the shipped product? A test that only runs behind a flag nobody sets, or a monitor bound to a no-op sink in production, is not a live guarantee. It may still be a perfectly good engineering artifact — but it is verifying the code, not watching the deployment.
Why this framing catches real errors An earlier version of the companion document What is Nostr implied that Buzz's own direct messages were end-to-end encrypted, because the Nostr specification NIP-17 sounds like it must apply. It does not. That mistake came from mapping a plausible spec onto a code path nobody had opened. Doing the check systematically — six properties, same three questions — is what this page is.

(a) Channel message content

What enforces it

A SQL predicate computed once per read request. When a client opens a Nostr REQ subscription, the relay builds a list of the channels that connection's public key may see, and pushes that list into the database query rather than filtering after the fact. The list comes from one function (crates/buzz-db/src/channel.rs:746-774) which is the union of two arms: rows in channel_members where the member has not been removed, and every channel whose visibility is 'open'. Both arms carry WHERE community_id = $1.

That vector is built at crates/buzz-relay/src/handlers/req.rs:88-106 and applied to the query at req.rs:291 via apply_access_scope_to_query. There is a further per-filter check at req.rs:376 for subscriptions naming an explicit channel.

The lookup is cached for ten seconds (crates/buzz-relay/src/state.rs:748-753, read at state.rs:1090-1107) with explicit invalidation on membership change, propagated across relay nodes (state.rs:864-895). So the worst case after removing someone, if the cross-node invalidation message is lost, is ten seconds of continued read access — not indefinite.

The part people get wrong Channel message content is not encrypted at rest and not encrypted in transit beyond ordinary TLS. The content column holds the plaintext. The protection is that the relay declines to select rows you are not entitled to. This is a real protection with a real threat model — it stops other users — but it fails differently from encryption: anyone with database access, or a bug in one query's predicate, reads everything. The one place the repository does store ciphertext in content is the NIP-ER event reminder kind (crates/buzz-db/src/event.rs:1390), which is self-encrypted by its author; that is the exception, not the rule.

What verifies it, and whether it is armed

This is where it gets interesting. There are 208 tests in the crates directory carrying #[ignore = "requires Postgres"]. The project's own test runner is explicit that nothing runs them (scripts/run-tests.sh:93-100):

# buzz-db migrator/lint unit tests (no infra) ... The Postgres-backed
# buzz-db tests are #[ignore]d; nothing here (or in integration mode below,
# which runs `cargo test -p buzz-db` without --ignored) runs them — they need a
# separate isolated-DB gate, so --lib keeps this step infra-free.

Continuous integration does reach into that pool, but by name, not wholesale. The backend integration job runs three narrow selections with --run-ignored ignored-only: the invite security tests, the NIP-ER reminder end-to-end binary, and a single named deletion-ordering test (.github/workflows/ci.yml:687-717). Everything else in the 208 is dark unless a developer runs it locally against a live Postgres.

My read This is a defensible engineering position — Postgres-backed tests are slow and the project has built cheaper substitutes (the migration lints and the conformance replay checker, both infra-free and both genuinely armed). But it means the sentence "the membership predicate is tested" is true of the test file and not of the pipeline. If you are evaluating Buzz for a deployment, the honest statement is: the read-path membership gate is enforced by code that is reviewed, formally modelled, and largely not exercised against a real database on every commit.

(b) DM content

What enforces it

Exactly the same thing as (a), because a Buzz direct message is a channel. The Desktop client's open_dm command publishes a kind:41010 event and the relay replies with an allocated channel id (desktop/src-tauri/src/commands/dms.rs:17-44; the kind constant is KIND_DM_OPEN at crates/buzz-core/src/kind.rs:494). From that point the conversation is ordinary kind:9 messages tagged with the channel via #h, stored in the same table, read through the same accessible_channels gate.

The most important correction on this page Buzz Desktop DMs are not end-to-end encrypted. Their confidentiality rests entirely on the relay's willingness to authorise a read. The relay operator can read every direct message on their server. This is a different security property from what most people mean by "DM", and it is the property that the naming does not advertise.

The precise wording matters here, because it is easy to overstate in the other direction. Nostr's gift-wrap primitive, kind:1059, is real production code in the Buzz relay: it is in the push-notification kind list (crates/buzz-relay/src/handlers/push_lease.rs:15), it has a dedicated authorisation carve-out in the read path (crates/buzz-relay/src/handlers/req.rs:937), and it has a match-time authorisation gate in the push runtime because — in the code's own words — "Kind 1059 is globally stored and leaks recipient activity through wake timing, so a lease may only match gift wraps addressed to its own author" (crates/buzz-relay/src/push_runtime.rs:289-291). Third-party Nostr clients can use gift-wrapped messaging against a Buzz relay.

What is absent is any use of it in the Desktop application's own DM-building path. A search of desktop/src-tauri/src for 1059 returns hits in exactly one file: desktop/src-tauri/src/archive/mod_tests.rs, where it appears as a subscription filter in an archive test. So: "gift wrap only exists in test files" is too strong. "The Buzz Desktop DM path does not use gift wrap" is correct.

(c) Channel membership

What enforces it

Rows in the channel_members table, which no client can write. This is the strongest of the six, and the mechanism is worth naming precisely: Buzz publishes membership as a Nostr event kind (kind:13534, the NIP-43 membership snapshot), but that kind is relay-only. A client that signs and submits its own snapshot claiming to be an owner is refused.

What verifies it, and whether it is armed

A live end-to-end test does precisely that attack (crates/buzz-test-client/tests/e2e_relay.rs:219-237). It first proves the actor can submit a normal event, so the subsequent rejection cannot be dismissed as a broad authorisation failure, then forges a kind:13534 snapshot tagging itself as owner and asserts the relay's reply is exactly "restricted: relay-only kind" — over WebSocket and over HTTP.

That test is named explicitly in the CI relay-e2e job (.github/workflows/ci.yml:755), running against a live relay. It is one of the few security invariants in this document with a genuine adversarial test that fires on every qualifying commit.

Verdict Membership is the property whose enforcement most closely matches what a reader would assume: server-authoritative state, client assertions rejected, an adversarial test armed in CI.

(d) Cross-community tenant isolation

This is the property with the largest gap between the documentation's sophistication and the code's actual defences — not because the code is bad, but because the documentation describes a two-layer defence and the second layer is unbuilt.

What enforces it

Three things, all at the application and schema level:

  1. Predicates. Every tenant-bearing query carries WHERE community_id = $1. The access-checker trait is documented with an unusually clear statement of why (crates/buzz-auth/src/access.rs:22-30): channel UUIDs are not globally unique, the primary key is (community_id, id), so a bare WHERE id = $1 would be "a cross-community existence oracle".
  2. Composite keys. Uniqueness and foreign-key constraints lead with community_id, so a conflict result cannot reveal the existence of another tenant's row.
  3. A migration lint. This is the clever part. Rather than trusting future authors to remember, a unit test parses the concatenated SQL of every embedded migration and rejects tables missing community_id, or scoped key constraints not led by it (crates/buzz-db/src/migration.rs:368-507, with the lint's own tests at 925-988). It runs in cargo test -p buzz-db --lib, needs no infrastructure, and is armed in CI.

What verifies it

Two artifacts, and they are serious. There is a TLA+ specification, docs/spec/MultiTenantRelay.tla, encoding a non-interference invariant — an observation made under community B's context must never carry a row labelled A. And there is an independent replay checker, the buzz-conformance crate, whose design note is worth quoting because it states the right ambition (crates/buzz-conformance/src/lib.rs:1-36):

Don't ask "did the model pass"; ask "did the running code emit a trace the model accepts."

The checker deliberately shares no type machinery with production — it defines its own community-label newtype rather than reusing buzz_core::CommunityId, on the stated grounds that a shared normalisation helper could hide its own bug from both the emitter and the judge. It also treats missing coverage as a failure: a critical seam exited without emitting a trace step is itself a breach, because "without it, trace conformance is decorative logging."

Whether it is armed — two separate answers

The replay checker is armed in CI, and deliberately inert in production. Production binds a no-op tracer (crates/buzz-relay/src/state.rs:799); the JSONL-emitting tracer is for conformance tests and the CI replay job (crates/buzz-relay/src/conformance/tracers.rs:1-2). That is a reasonable design — it is a verification of the code, not a runtime intrusion detector — but it means no deployed Buzz relay is checking its own traces against the model while serving traffic.

The headline finding: the fail-closed backstop does not exist

The non-interference proof is explicitly stated as holding relative to a set of axioms, and the first block of them is Postgres row-level security (docs/multi-tenant-relay.md:350-374). A-RLS-1 requires every tenant-bearing table to have RLS enabled with a restrictive policy community_id = current_setting('app.community_id')::uuid. A-RLS-2 requires the relay's database role to be non-superuser and NOBYPASSRLS. A-RLS-3 requires app.community_id to be set transaction-locally before any query. The document is precise about why this matters:

A query that fails to set app.community_id matches the policy predicate over NULL → no rows, never all rows. This is what makes a missed application predicate fail closed rather than leak.

The design document says these are "admitted by a startup/CI assertion suite" that enumerates every tenant-bearing table and "A failing assertion rejects the deployment" (docs/multi-tenant-relay.md:655-660).

Neither the RLS nor the assertion suite is present in the repository. Searching every migration in migrations/ for ROW LEVEL SECURITY or CREATE POLICY returns nothing. Searching crates/, scripts/, .github/ and deploy/ for NOBYPASSRLS returns nothing. Searching crates/buzz-db for set_config('app.community_id'…) returns nothing — the only set_config calls set unrelated session variables (buzz.created_at_floor, buzz.nip_rs_hard_delete).

Consequence, stated plainly: a query that forgets its WHERE community_id predicate today fails open, returning every tenant's matching rows, not closed. The single mechanism enforcing tenant isolation is therefore application-level discipline plus composite keys plus a migration lint — a good three-layer story, but one layer thinner than the proof's own stated premise. This is my inference from the absence of the code; the document may describe an obligation the project intends to place on the operator rather than ship, but no deployment chart, script, or startup check in the repository establishes it either.

(e) Agent authority to act

Buzz's distinguishing claim is that AI agents are members of a workspace rather than webhooks bolted onto it. That makes "what is an agent allowed to do" a first-class security question, and it is the softest of the six.

Layer one: scopes (real, but incomplete)

There is a proper OAuth-style scope enum — MessagesRead, MessagesWrite, AdminChannels, FilesWrite and so on (crates/buzz-auth/src/scope.rs:16-56). Two of its variants document their own gaps, which is admirable and also load-bearing: ReposRead is "Reserved for future use. Not currently enforced by git HTTP routes" (scope.rs:46-50), and ReposWrite is enforced on WebSocket ingest but "NOT enforced by git HTTP push routes" (scope.rs:51-56). Those routes fall back to NIP-98 auth plus an owner check instead. So the scope vocabulary is wider than the scope enforcement.

Layer two: the event filter (real, narrow)

Which events reach an agent at all is decided by boolean expressions evaluated over event fields — content, author, kind, channel, timestamp — with a hard timeout and a length bound (crates/buzz-acp/src/filter.rs:1-50). First matching subscription rule wins. This is a genuine gate, but it governs input selection, not what the agent may do once triggered.

Layer three: the prompt (not a fence)

The rest of the agent's constraints live in crates/buzz-acp/src/base_prompt.md as prose: never post to a different channel than the one you were tagged in, do not format mentions with bold or backticks, never publish a bare acknowledgement, never run recursive searches over $HOME. These are instructions to a language model. They are requests. A model that ignores them has broken no fence.

The gap: permission prompts are auto-approved

Buzz drives real agent CLIs — Claude Code, Codex, Goose — over the Agent Client Protocol. Those CLIs raise a session/request_permission request before a sensitive tool call: the human-in-the-loop moment. Buzz's bridge answers it automatically. The handler at crates/buzz-acp/src/acp.rs:1856-1900 is documented as "Auto-approve a session/request_permission request from the agent"; it locates the option whose kind is allow_once and responds with that option's id, falling back to reject_once only if no allow option is offered. There is no policy check, no allowlist, no owner consultation.

The engineering care in that function is real — it never hardcodes an option id, it handles both numeric and string JSON-RPC ids, it guards a double-response race. It is careful code that implements "always yes".

The compounding gap: untrusted text sits in the instruction plane Channel content reaches the agent by direct string interpolation. The prompt block is built as "Event ID: … Channel: … Kind: … From: … Time: … Content: {content}" at crates/buzz-acp/src/queue.rs:1097-1109, with the event's tags serialised in immediately after. There is no escaping, no delimiter, no untrusted-data preamble, no structural separation between the operator's instructions and text that any channel member — or anyone who can get a message into a channel an agent watches — controls. Combined with unconditional permission approval, the practical bound on what a Buzz agent will do is whatever sandbox the underlying CLI enforces on its own, not anything Buzz imposes.

What verifies it

Unit tests on filter evaluation and on scope checks. Nothing verifies the prompt, because nothing can: there is no test that asserts a language model obeys a paragraph. This is not a Buzz failing so much as a property of the category, but it is the reason the agent plane — not the relay — is where the trust boundary is thin.

(f) Media blob access

Uploads and downloads have completely different security postures, and the asymmetry is the finding.

Uploads: strongly gated

An upload must present a Blossom kind:24242 authorisation event, and the extractor validates it before a single byte of the body is buffered — deliberately, so an unauthenticated caller cannot force the server to read a large body (crates/buzz-relay/src/api/media.rs:26-32). Validation covers the Schnorr signature, the kind, the verb tag, a future expiration, a past created_at with five seconds of clock-skew tolerance, and the server-domain tag (crates/buzz-media/src/auth.rs:20-70). Then the X-SHA-256 header must match an x tag inside the signed event, so the authorisation is bound to this exact blob. Then NIP-43 relay membership is enforced, described in the code as "the only upload authority: independent of bearer-token / api_tokens storage" (media.rs:203-218). Then a rate limit and a concurrency permit. Five gates.

Downloads: open by default

The corresponding read gate is behind a config flag that ships off. require_media_get_auth is documented as "Require Blossom kind:24242 t=get auth plus relay membership before serving media GET/HEAD. Default off for staged client rollout" (crates/buzz-relay/src/config.rs:212-214), read from BUZZ_REQUIRE_MEDIA_GET_AUTH at config.rs:742-748. A config test asserts the default and explains it: assert!(!config.require_media_get_auth, "require_media_get_auth should default to false for staged client rollout") (config.rs:1037-1040).

With the flag off, authenticate_media_read binds the tenant from the request host and returns immediately, skipping both the Blossom check and the membership check (crates/buzz-relay/src/api/media.rs:494-498). The response is served with Cache-Control: public, max-age=31536000, immutable rather than private (media.rs:517-521), so intermediaries may cache it.

So the default access control on a Buzz media blob is knowledge of its SHA-256 hash. That is a capability URL: a 256-bit unguessable secret, which is genuinely strong against brute force and genuinely weak against every way a URL leaks — a pasted link, a Referer header, a browser history sync, a screenshot, a cache. Channel membership is not consulted. A file shared into a private channel is retrievable by anyone who obtains its hash, from outside the community, with no credential at all.

My read The flag's own comment tells you this is a migration in progress: the enforcement is written, tested and ready, and it is off so that clients that do not yet send Blossom get-auth headers keep working. That is a normal staged rollout. But "written and off" is exactly the state this document exists to catch, and an operator reading ARCHITECTURE.md would not discover it. If you self-host Buzz and care about attachment confidentiality, set BUZZ_REQUIRE_MEDIA_GET_AUTH=true and verify your clients still work.

One artifact deserves a note of genuine credit. The audit log (crates/buzz-audit/src/lib.rs:1-18) is a per-community SHA-256 hash chain in which the community id is folded into the hash, so — in the crate's own words — "a row lifted out of one community's chain can never verify inside another's; chain identity carries the tenant." Writes are serialised by a per-community Postgres advisory lock rather than one global lock, which avoids making every tenant's write latency observable to every other tenant. That is a timing-side-channel consideration most projects would not have made, and it is on by default.

Where the documents have drifted from the code

Two drifts surfaced during this pass. In both, the code is newer and safer than the document.

The get_accessible_channel_ids "landmine" is fixed. The TLA+ specification's source-grounding note states that this function "currently unions all open channels in the DB; that unscoped variant is the explicit I1 mutation" (docs/spec/MultiTenantRelay.tla:38-40), and the design document repeats it, citing crates/buzz-db/src/channel.rs:545-560 (docs/multi-tenant-relay.md:896-899). The function now lives at channel.rs:746-774 and both of its arms carry WHERE community_id = $1. The hazard the documents warn about no longer exists in the code they cite. This is the healthy direction of drift, but it means a reader trusting the spec's source notes would be hunting a fixed bug.

The RLS backstop drifts the other way. Unlike the case above, here the document describes something stronger than the code provides — see (d). That is the drift direction that matters, and it is the one to re-check on every future pass.

These join the two drifts already recorded in the companion documents: the rate-limiting description and the MAX_FRAME_BYTES value in ARCHITECTURE.md. The working rule for this repository holds — when the documents and the code disagree, the code is newer — but the RLS case shows the rule is not a safety guarantee, only a recency one.

The honest one-paragraph summary

Buzz's confidentiality is authorisation, not encryption. Channel messages and direct messages alike are plaintext rows in Postgres, protected by a membership predicate the relay pushes into every read query; the relay operator can read everything, and the difference between a private channel and a public one is a WHERE clause, not a key. Membership itself is the strongest link — server-authoritative, client assertions rejected, adversarially tested in CI on every commit. Tenant isolation is enforced by three real application-and-schema layers and modelled by a serious TLA+ specification with an independent replay checker, but that proof is stated relative to a Postgres row-level-security backstop that is not present anywhere in the repository, so a forgotten predicate fails open rather than closed. Media uploads pass five gates; media downloads pass none by default, making the SHA-256 hash the entire access control. And agent authority — the thing that makes Buzz distinctive — is bounded by scopes with documented enforcement gaps, an input filter, a prompt file that is a request rather than a fence, an ACP bridge that auto-approves every permission request the agent raises, and raw attacker-controllable channel text interpolated straight into the instruction plane. None of this makes Buzz unsound for its stated purpose, which is a self-hosted workspace among people who already trust the operator. It does mean that four of the six properties — DM content, tenant isolation, agent authority, and media access — are weaker or differently shaped than a careful reader of ARCHITECTURE.md would assume, and each of those four has a concrete, actionable fix: publish the authorisation model honestly, ship the RLS policies, gate agent permissions, and flip BUZZ_REQUIRE_MEDIA_GET_AUTH on.
