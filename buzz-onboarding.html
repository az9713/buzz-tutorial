The mental model

Three ideas explain almost every design decision in Buzz. Learn these and the rest of the app stops being surprising.

1. It's a chat app built on Nostr, not on a company's server

Your identity is a cryptographic keypair, not an account on someone's database. Messages are signed Nostr events published to a relay — a server that stores and forwards them. A "community" in Buzz is really just a relay URL plus a token. You can belong to several at once, and the community rail on the far left switches between them.

The practical consequence: nobody can reset your password, because there isn't one. Your keypair is the account. Settings says so plainly — "Your keypair and NIP-05 handle are fixed for this device." Back the key up before you do anything else.

2. Agents are members, not features

The coding agents (Claude, Codex, Grok, Hermes and others) join channels the way people do. They get a pubkey, an avatar, and a line in the member list. When you write @Grok please remind me what this project is about, you are mentioning a participant, and the reply lands in a thread like any other reply. "Managed by you" on an agent means the process runs on your machine under your key.

3. Automation splits into two very different tools

People conflate these constantly, so be precise:

Agents

Judgement. An LLM reads context and decides what to do. Costs tokens. Non-deterministic. Use for "read this and tell me what's wrong."

Workflows

Rules. A YAML file says when-this-then-that. Free, deterministic, auditable. Use for "when someone says P1, post an alert."

The power-user move is combining them: a workflow does the reliable trigger-and-route, and one of its steps pokes an agent.

Binding a project to a channel

The strongest pattern in Buzz, and the one the screenshot in your own install demonstrates: bind a repo to a channel so that repo activity and the conversation about it share one place. The channel welcome message then reads like "The Buzz repo lbm-wind-tunnel is bound here (source: github.com/…, main @ 6d9a8b6)" — and agents in that channel inherit the repo as working context.

Power move One channel per repo, repo bound, agents added to the channel. Now "@Claude why did the last commit break the build?" has everything it needs without you pasting a single path. This is the single highest-leverage setup in the whole app.
Routes Projects has its own URL space — /projects and /projects/$projectId — so back/forward (Alt+← / Alt+→) work properly inside it.

Talking to an agent

Mention it in any channel it belongs to. The reply arrives as a thread on your message, so a channel with four agents doesn't become unreadable:

@Grok please briefly remind me what this project is about

Watch a run live via the session panel — it streams tool calls, file edits with diffs, and the raw event rail if you want to see the underlying Nostr events. That transparency is unusual and worth using when an agent does something you didn't expect.

Read before you scale this up An independent security audit of this repo (2026-08-01) found that the managed-agents subsystem — about 37,000 lines of Rust, including the codebase's unsafe blocks — had no lint coverage and was never properly reviewed. Nothing bad was found there; the auditors were explicit that this means nothing, because nobody looked properly. Separately, no reviewer examined indirect prompt injection, the risk class where an agent reads attacker-controlled text and acts on it. Treat agents with repo write access and channel content they didn't author as an unproven combination.

Anatomy of a workflow

name: Human readable name        # required, non-empty
description: Optional one-liner  # optional
enabled: true                    # optional, defaults to true
trigger:
  on: message_posted             # one of five, see below
steps:                           # required, at least one
  - id: step_one                 # letters, digits, underscore ONLY. Max 64 chars.
    name: Optional label
    if: 'str_len(trigger_text) > 5'   # skip (not fail) when false
    timeout_secs: 60
    action: send_message
    text: 'Hello'

Eight recipes to paste

All eight validate against the schema in schema.rs. Change the names and channel-specific values; the structure is ready to run.

1 — Daily standup prompt

The friendliest possible starting point: it can't break anything and you'll see it work tomorrow morning. Cron is UTC, so translate your local time.

name: Daily Standup
description: Weekday nudge at 09:00 UTC
trigger:
  on: schedule
  cron: '0 9 * * 1-5'
steps:
  - id: prompt
    action: send_message
    text: |
      Standup time. Three lines each:
      1. Shipped yesterday
      2. Doing today
      3. Blocked on

2 — P1 escalation with branching

Shows filtering at the trigger and branching between steps. The trigger filter keeps the engine from waking up at all for ordinary chatter; the if then splits behaviour.

name: Incident Escalation
description: React and shout when a P1 or SEV1 appears
trigger:
  on: message_posted
  filter: 'str_contains(trigger_text, "P1") || str_contains(trigger_text, "SEV1")'
steps:
  - id: ack
    action: add_reaction
    emoji: rotating_light
  - id: escalate
    if: 'str_contains(trigger_text, "SEV1")'
    action: send_message
    text: 'SEV1 declared by {{trigger.author}} — paging the on-call rota now.'
  - id: normal
    if: '!str_contains(trigger_text, "SEV1")'
    action: send_message
    text: 'P1 logged. Someone pick this up: {{trigger.text}}'

3 — Reaction-driven triage

A team convention with zero process overhead: anyone who reacts 📋 to a message turns it into tracked work. The reaction becomes the button.

name: Clipboard Triage
description: React with :clipboard: to escalate a message into triage
trigger:
  on: reaction_added
  emoji: clipboard
steps:
  - id: seen
    action: add_reaction
    emoji: eyes
  - id: announce
    action: send_message
    text: 'Triage requested on a message from {{trigger.author}}. Original: {{trigger.text}}'

4 — Deploy approval gate

The most valuable pattern in the whole engine. request_approval genuinely suspends the run — it doesn't poll or block a thread — and resumes when a human answers or the timeout expires. The request appears under Inbox → Needs action.

name: Deploy Approval
description: Ask a human before a deploy proceeds
trigger:
  on: webhook
steps:
  - id: request
    action: request_approval
    from: '@engineering-lead'
    message: 'Deploy to production? Triggered by CI.'
    timeout: 4h
  - id: notify_approved
    if: 'steps_request_output_approved == true'
    action: send_message
    text: 'Deploy APPROVED. Proceeding.'
  - id: notify_denied
    if: 'steps_request_output_approved == false'
    action: send_message
    text: 'Deploy DENIED. Holding at current release.'
Reading a previous step's output Note the flattened variable name: steps_request_output_approved, where request is the step id. In templates you'd write the dotted form {{steps.request.output.approved}}, but in an if: expression it must be underscores. This catches everyone once.

5 — Diff review nudge

Uses the trigger unique to a developer chat tool: diff_posted fires on posted code diffs, and its filter sees the diff text — so you can watch specific paths.

name: Sensitive Path Watch
description: Speak up when a diff touches auth or crypto code
trigger:
  on: diff_posted
  filter: 'str_contains(trigger_text, "src/auth/") || str_contains(trigger_text, "crypto")'
steps:
  - id: flag
    action: add_reaction
    emoji: warning
  - id: request_review
    action: send_message
    text: |
      This diff touches a sensitive path and needs a second reviewer
      before merge. Author: {{trigger.author}}

6 — Welcome DM for first posters

Demonstrates send_dm addressed to the person who triggered the run. Quiet onboarding — nothing clutters the channel.

name: Newcomer Welcome
description: DM anyone whose message contains an introduction marker
trigger:
  on: message_posted
  filter: 'str_starts_with(trigger_text, "intro:")'
steps:
  - id: greet
    action: add_reaction
    emoji: wave
  - id: dm
    action: send_dm
    to: '{{trigger.author}}'
    text: |
      Welcome aboard. Two things worth doing now:
      1. Settings → Profile → set a display name
      2. Settings → Personal → back up your private key
      Ask me anything in the channel.

7 — Slow heartbeat with a delay

Shows interval and delay together. The interval minimum is 60 seconds and the definition is rejected below that, because the scheduler only ticks once a minute.

name: Hourly Focus Check
description: Hourly nudge, with a short pause before the follow-up
trigger:
  on: schedule
  interval: 1h
steps:
  - id: ping
    action: send_message
    text: 'Hourly check: is the top of the board still the right top of the board?'
  - id: wait
    action: delay
    duration: 5m
  - id: followup
    action: send_message
    text: 'If nobody has re-ranked in five minutes, assume yes and keep going.'

8 — Outbound webhook (elevated privilege)

Forwards channel content to an external system. Read the warning below before using this one — it is the only action in the engine with a special authority rule.

name: Incident Bridge
description: Forward incident declarations to the external pager
trigger:
  on: message_posted
  filter: 'str_contains(trigger_text, "SEV1")'
steps:
  - id: page
    action: call_webhook
    url: https://hooks.example.com/incident
    method: POST
    headers:
      Content-Type: application/json
    body: '{"severity":"sev1","author":"{{trigger.author}}","text":"{{trigger.text}}"}'
call_webhook requires owner or admin authority Being a channel member is not enough — to save or run a workflow containing call_webhook you need elevated channel authority. The reason is stated in the source: a workflow forwards channel content using the owner's standing authority long after it was saved, so an ordinary member could otherwise install a permanent data-exfiltration pipe. The URL must be a public HTTPS endpoint. crates/buzz-workflow/src/schema.rs:149–161 (SEC-006)

Variables & expressions

Two syntaxes exist for the same data, and using the wrong one in the wrong place is the most common workflow bug.

DataIn text (templates)In if: / filter:
Message text{{trigger.text}}trigger_text
Author pubkey{{trigger.author}}trigger_author
Channel id{{trigger.channel_id}}trigger_channel_id
Timestamp{{trigger.timestamp}}trigger_timestamp
Emoji{{trigger.emoji}}trigger_emoji
Message id{{trigger.message_id}}trigger_message_id
Step output{{steps.ID.output.FIELD}}steps_ID_output_FIELD

crates/buzz-workflow/src/executor.rs:208–216

Why the difference: the expression engine (evalexpr) can't parse dotted identifiers, so dots become underscores. That's also why step ids may only contain letters, digits and underscores — a step called my-step would be read as my minus step.

The four string functions

FunctionReturns
str_contains(haystack, needle)bool
str_starts_with(s, prefix)bool
str_ends_with(s, suffix)bool
str_len(s)int

Combine with &&, ||, !, and the usual comparisons. These four are registered by Buzz specifically because the expression library doesn't ship them — so don't expect other string helpers to exist.

Six traps, straight from the validator

Each one is enforced by a test in the source. Knowing them saves an afternoon.

  1. Step ids reject dashes. my-step fails validation. Underscores only, max 64 characters, and duplicates are rejected.
  2. Intervals under 60 seconds are refused. interval: 30s fails at save time with a message about the 60-second minimum — the scheduler ticks once a minute, so a shorter interval could never fire correctly.
  3. You cannot post to another channel. For a channel-scoped workflow, a channel: override must be a valid UUID and must equal the workflow's own channel, otherwise the run errors. Just omit the field.
  4. Unknown template variables stay as literal text. A typo like {{trigger.txt}} doesn't error — it posts the string {{trigger.txt}} into your channel. Check the first run's output.
  5. Cron is UTC and accepts 5, 6, or 7 fields. Five fields (min hour dom month dow) get a seconds field prepended and a year appended automatically.
  6. cron and interval are mutually exclusive. Supplying both, or neither, fails validation.
Debugging routine Open the workflow → Execution Trace. It shows each step and whether it ran, was skipped by its if, or failed. A skipped step is not an error — that distinction is deliberate in the engine and it's usually the answer to "why did nothing happen?"

Organising the sidebar

Four independent mechanisms, all per-user and all invisible to everyone else:

  • Star — pulls a channel into a "Starred" group pinned above everything.
  • Sections — your own named groups with icons. Drag channels between them; reorder the sections themselves.
  • Sort mode — set per group, not globally. Starred can sort by activity while Channels sorts alphabetically.
  • Mute — stays in the list, stops generating noise.
Power move Sections plus per-section sort is the feature that makes Buzz scale past ~30 channels. Make a section per project, drag its channels in, sort it by recent activity, and collapse the ones you're not on this week.

Forums

Channels with channelType: forum — threaded, post-and-reply, for discussions that should stay findable rather than scroll past. They get their own sidebar group and their own route (/channels/$channelId/posts/$postId), so an individual post is a linkable destination.

Your first week

Ordered so each step makes the next one useful. Nothing here is speculative — every action maps to a feature documented above.

Day 1 — Don't lose the account

  1. Ctrl+, → Personal → Profile → set a display name.
  2. Same page → Identity → back up your private key somewhere off this machine. Non-negotiable.
  3. Personal → Appearance → pick a theme.
  4. Personal → Notifications → turn off "notify while viewing".

Day 2 — Make the sidebar survivable

  1. Shift+Ctrl+O → join what's relevant, ignore the rest.
  2. Right-click your three most important channels → Star.
  3. Create one section per project; drag channels in.
  4. Mute anything you read but never act on.

Day 3 — First workflow

  1. Sidebar → Workflows → Create Workflow.
  2. Pick a low-traffic channel. Click Edit as YAML.
  3. Paste recipe 1 (Daily Standup). Create.
  4. Tomorrow, open it and read the Execution Trace. You now understand the whole engine.

Day 4 — First agent

  1. Ctrl+, → App → Agents → set provider, model and API key in Agent defaults.
  2. Sidebar → Agents → New → pick a harness → Create.
  3. Add it to one channel. Mention it. Watch the session panel stream.

Day 5 — Wire code to conversation

  1. Projects → New → create or bind a repository.
  2. Make a channel for it; bind the repo.
  3. Add your agent to that channel. Ask it something about the repo — no paths, no pasting.
  4. Add recipe 5 (Sensitive Path Watch) with your own paths.

Day 6–7 — Compound it

  1. Personal → Local archive → turn on for channels holding decisions.
  2. Communities → Templates → save your project-channel shape as a template.
  3. App → Compute → if you have the GPU for it, share the machine.
  4. Add recipe 4 (Deploy Approval) and watch it land in Inbox → Needs action.

What this doc doesn't cover

Stated plainly so you know where the edges are, rather than discovering them the hard way.

  • Depth on Agents. The Agents interface is around 40,000 lines — roughly a third of the entire desktop UI — on top of a large Rust subsystem. This document covers the concepts and the main paths, not every dialog. MCP servers, agent memory, team snapshots and the ACP custom-harness form each deserve their own page.
  • Mobile and web clients. Everything here is the desktop app at v0.5.3. The mobile client has its own screens.
  • Relay operation. Running your own relay, mesh relay topology and the admin console are separate subjects with their own docs in the repository.
  • The Nostr protocol layer. Event kinds and the NIP specifications live in the repo's docs/nips/. You don't need them to use Buzz; you do need them to extend it.
  • Security review status. As noted under Agents, the managed-agents subsystem was never properly reviewed, and no audit lens examined indirect prompt injection. That's a known gap in the project's assurance, not in this document.
