Hardening Buzz

A remediation companion to the trust map. For each gap it found: what an operator can do today without touching code, what the upstream change would actually be, what it would cost, and — for one of them — why I think attempting it would be a mistake.

Status of this document This is an advisory, not a patch series. Nothing here has been submitted to block/buzz, and the analysis was produced by reading the public repository, not by working on it. Two of the five items below are operator actions that take effect immediately and require no upstream cooperation at all — those are the ones to act on first.

Do these two things today

Everything else in this document depends on someone else accepting a change. These two do not. If you run a Buzz relay, they are available to you right now.

1. Turn on media download authorisation 
BUZZ_REQUIRE_MEDIA_GET_AUTH=true

This flips require_media_get_auth (crates/buzz-relay/src/config.rs:742-748) from its shipped default of false. With it on, a media GET must present a Blossom kind:24242 t=get authorisation event bound to that blob's hash, and the requester must pass the NIP-43 relay membership check (crates/buzz-relay/src/api/media.rs:500-512). Responses also switch from Cache-Control: public to private (media.rs:517-521), so intermediaries stop caching them.

Test before you commit to it. The default is off for a stated reason — "staged client rollout" — which means some client versions do not yet send the get-auth header and will start failing to load attachments. Turn it on in staging, exercise every client you actually deploy (Desktop, mobile, any bot using buzz-cli), then roll it forward.

2. Decide, deliberately, who your agents can be spoken to by

There is no flag for this one, because the gap is structural: a Buzz agent auto-approves its own permission requests and receives channel text as undelimited instructions. What you can control is the input side — the subscription filter expressions that decide which events reach an agent at all (crates/buzz-acp/src/filter.rs:1-50). Treat any channel an agent watches as a channel where any member can issue instructions to that agent with the agent's own privileges. Scope agent membership to channels whose membership you would trust with the agent's credentials, and do not put agents in channels open to guests or to federated/unknown pubkeys. This is a deployment discipline, not a fix, and it is the only lever available today.

Gap 1 — untrusted text in the agent instruction plane

What is wrong

Event content reaches the agent by direct interpolation. The prompt block is assembled as "Event ID: … Channel: … Kind: … From: … Time: … Content: {content}" at crates/buzz-acp/src/queue.rs:1097-1109, with the event's tags serialised straight in after it. Nothing marks where operator instructions end and member-supplied text begins. Any member of a channel an agent watches can write text that the model has no structural reason to treat differently from its own system prompt.

Why this one is first

The project already solved this exact problem elsewhere, and the fix is in-tree to copy. When buzz-agent folds post-compact hook output into a conversation, it wraps it explicitly — handoff_text.push_str("\n\n[Post-compact hook output — untrusted]\n") at crates/buzz-agent/src/handoff.rs:83-89 — and there is a regression test asserting the marker survives (crates/buzz-agent/tests/regressions.rs:1108, 1199). So the pattern, the wording convention, and the test shape all exist. This is not a design proposal; it is applying an existing house rule to a place that missed it.

The change

  • Wrap the interpolated content and tags in an explicit delimited block with an untrusted label, matching the handoff.rs wording convention.
  • Strip or escape any sequence in the content that would forge the block terminator or a section header (the prompt's sections self-delimit on [Header] lines — see the assembly contract documented at queue.rs:1386-1403 — so a message body containing a line like [System] is currently indistinguishable from a real section).
  • Add a regression test in the shape of the existing one: publish content containing a forged header, assert it arrives neutralised.

Cost and risk

Around thirty lines and one test. The risk is cosmetic — agents see slightly more prompt scaffolding — and it costs a small number of tokens per turn. There is a real second-order consideration worth raising in any PR rather than deciding unilaterally: the observer frame's size trimmer elides oversized sections in place (queue.rs:1396-1401), so a new wrapper needs to survive trimming rather than be the thing that gets trimmed.

Gap 2 — media downloads open by default

What is wrong

require_media_get_auth ships false (crates/buzz-relay/src/config.rs:212-214 and :742-748, with a test asserting the default at :1037-1040). With it off, authenticate_media_read binds the tenant from the request host and returns immediately, skipping both the Blossom check and the membership check (crates/buzz-relay/src/api/media.rs:494-498). The effective access control on a blob is knowledge of its SHA-256 — an unguessable capability, but one that leaks through every channel a URL leaks through.

Why the obvious fix is the wrong fix Flipping the default to true would break every deployed client that does not yet send a get-auth header — which is precisely why it is false. A patch that flips it is a patch that says "I did not read the comment." The staged rollout is legitimate; what is missing is that nothing tells an operator they are in the unsafe half of it.

The change

Emit a startup warning, exactly mirroring the one the same file already emits for a comparable weakened default (config.rs:637-641):

if !require_media_get_auth {
    warn!(
        "BUZZ_REQUIRE_MEDIA_GET_AUTH is false — media GET/HEAD serves blobs to \
         anyone who knows the SHA-256, with no Blossom auth and no membership \
         check, and responses are cached publicly. Set to true for production \
         once all clients send Blossom get-auth."
    );
}

Optionally, document the flag in the deployment chart's values and in whatever security-configuration page the project maintains. The default itself stays untouched.

Cost and risk

Five lines, no behaviour change, no client breakage, and it mirrors existing code so closely that reviewing it is trivial. Of the upstream changes on this page, this is the one most likely to be accepted as-is.

Gap 3 — agent permission requests auto-approved

What is wrong

Agent CLIs driven over the Agent Client Protocol raise session/request_permission before a sensitive tool call — the human-in-the-loop moment. Buzz's bridge answers automatically: it finds the option whose kind is allow_once and returns that option's id, falling back to reject_once only if no allow option is offered (crates/buzz-acp/src/acp.rs:1856-1900). There is no policy consulted, no allowlist, no owner notified. Combined with Gap 1, the practical bound on a Buzz agent's authority is whatever sandbox the underlying CLI enforces on its own.

Why this is harder than it looks

"Always yes" is very likely deliberate. An agent that is a workspace member and stops to ask its owner before every file read is not usable as a member; the whole product premise pushes toward autonomy. Replacing the behaviour therefore requires answering a product question that the repository does not answer and that an outside contributor should not answer for it: who approves, through what surface, and what happens while waiting. Routing the prompt back to the owner as a Nostr event, for instance, means defining a new kind, a timeout, and a default-on-timeout — a NIP-sized decision, not a patch.

The change I would actually propose

The minimum honest version keeps today's behaviour as the default and makes it visible and overridable:

  • Introduce a permission policy enum with three values — AutoApprove (today's behaviour, and the default), DenyAll, and Allowlist(Vec<String>) matching on the ACP permission's tool name.
  • Read it from configuration per agent, defaulting to AutoApprove so no existing deployment changes behaviour.
  • Log every auto-approval at info with the tool name — the handler already logs at that level (acp.rs:1896-1899), so this is largely a matter of ensuring the tool name is in the line, making after-the-fact audit possible even when the policy is permissive.
  • Record approvals in the existing tamper-evident audit log (crates/buzz-audit/src/lib.rs:1-18) rather than inventing a new trail.

Cost and risk

Moderate — a config surface, a policy type, wiring through the pool, tests. The risk is not technical but social: it is a contributor telling a project how its central UX decision should be configurable. It lands far better as an issue that asks the question than as a PR that answers it.

Gap 4 — the Postgres test pool is dark

What is wrong

208 tests carry #[ignore = "requires Postgres"], and the project's own runner states plainly that nothing runs them (scripts/run-tests.sh:93-100): the Postgres-backed buzz-db tests "need a separate isolated-DB gate." CI reaches into the pool by name for three narrow selections only (.github/workflows/ci.yml:687-717). The membership predicate, the tenant-scoping queries, deletion semantics and moderation are all covered by tests that do not run on a commit.

The change

A CI job with a Postgres service container that runs cargo nextest run -p buzz-db --run-ignored ignored-only against an isolated database. The infrastructure to do this already exists in the workflow — the backend integration job stands up Postgres via docker compose, waits on health, and runs targeted --run-ignored selections (ci.yml:592-717). This is widening an existing pattern, not inventing one.

Why it is not first

Almost certainly some of the 208 currently fail or are flaky — that is the usual reason a pool goes dark and stays dark. A contributor who turns the job on hands the maintainers a red build and a pile of triage they did not ask for. The right sequence is: run them locally against a throwaway database, report which fail, and let the maintainers decide whether to fix or to quarantine. That is a reasonable next piece of work and it needs no permission — it happens entirely in a local clone.

Gap 5 — the absent RLS backstop, and why not to build it

What is wrong

This is the most serious finding in the trust map and the one I recommend not attempting. The tenant-isolation proof is stated relative to axioms A-RLS-1 through A-RLS-5 (docs/multi-tenant-relay.md:350-374), which require Postgres row-level security with a restrictive policy on every tenant-bearing table, a non-superuser NOBYPASSRLS request role, and app.community_id set transaction-locally before any query. The document is explicit about what that buys:

A query that fails to set app.community_id matches the policy predicate over NULL → no rows, never all rows. This is what makes a missed application predicate fail closed rather than leak.

None of it exists. No ROW LEVEL SECURITY or CREATE POLICY in any migration; no NOBYPASSRLS anywhere in crates/, scripts/, .github/ or deploy/; no set_config('app.community_id', …) in buzz-db. Nor does the "startup/CI assertion suite" that docs/multi-tenant-relay.md:655-660 says admits these axioms. So a forgotten predicate fails open.

Why I advise against building it as an outside contribution
  • A-RLS-3 is the trap. It requires tenant context to be set transaction-locally and never retained or combined across requests on a pooled connection. Get this subtly wrong — a SET instead of a SET LOCAL, a query that borrows a connection outside the transaction, a background task reusing a pooled handle — and you get a system that passes every test and cross-contaminates tenants under concurrency. That failure is worse than the status quo, because the status quo at least has no false assurance attached.
  • A-RLS-4 requires an audit we cannot perform from outside. Every SECURITY DEFINER and leakproof function in the request path has to be reviewed as part of the trusted boundary, because a leakproof function may be evaluated ahead of the policy check. That is a whole-codebase review with production context we do not have.
  • It changes the deployment contract. A non-superuser, non-owner (or FORCE ROW LEVEL SECURITY) request role means every existing operator's database provisioning has to change. That is a breaking operational change that only the maintainers can sequence and communicate.
  • We cannot verify it. See Gap 4 — the test pool that would catch a regression here is exactly the pool that does not run.

What is worth doing instead

Build the assertion, not the enforcement. A startup or CI check that enumerates tenant-bearing tables and reports whether RLS is enabled with a restrictive policy, whether the connected role is NOBYPASSRLS, and whether app.community_id is set — failing loudly, or at minimum warning loudly, when the answer is no. This is honest: it does not pretend to close the gap, it makes the gap impossible to be unaware of, and it is precisely the artifact docs/multi-tenant-relay.md:655-660 already says should exist. It is also small, self-contained, and carries none of the risks above, because it changes no query path.

The enforcement itself belongs to whoever owns the deployment contract and can run the tests. The right outside contribution is the report, plus the check that keeps the report true.

What a good upstream report would say

If this goes to block/buzz, it should go as issues rather than as a PR, and it should separate the four findings by how much agreement they need. One procedural point first: the project's SECURITY.md opens with "Please do not report security vulnerabilities through public GitHub issues" and directs reporters to its private channel. Nothing here is a zero-day — every fact is derived from the public repository and several are documented by the project itself — but the media download default is the item most plausibly in scope, so route that one privately first and let the maintainers say whether the rest can be public.

My read on the whole exercise None of these findings suggest carelessness. The repository contains a TLA+ specification, an independent replay checker built specifically so a buggy helper cannot launder its bug into the judge, a per-community hash-chain audit log with per-tenant advisory locks chosen to avoid a timing side channel, and migration lints that fail the build when a future table forgets its tenant column. That is a higher standard of security engineering than most projects reach. The gaps are the ordinary kind: a staged rollout whose unsafe half is silent, a convention applied in one crate and not another, an autonomy decision with no configuration surface, and a proof whose assumptions outran the schema. Naming them precisely is more useful than patching them imprecisely.
